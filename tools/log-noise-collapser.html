Log Noise Collapser

Log Noise Collapser

Paste a log dump (or drop a .log file) and it collapses thousands of near-identical lines into the handful of distinct failures underneath. Variable parts — timestamps, UUIDs, IPs, hex addresses, line numbers — get masked, then a 22 MB sentence-embedding model runs inside your browser tab and groups what's left by meaning, so reading 'id' and reading 'email' from the same broken handler land in one group instead of two.

Free tier: your own CPU/GPU does the inference — there is no API and no key, so there is no per-request quota to run out of. The one network call is the initial ~22 MB model download from the Hugging Face Hub, which for anonymous users is rate-limited to 3,000 file-resolve requests per 5-minute window per IP (this tool uses ~6 of them, once, then the browser caches it). Logs never leave the tab.

What it replaces

Grouping repeated log lines into distinct patterns is a paid feature in log platforms. Datadog's Log Management prices Standard Indexing at $1.70 per million log events per month (15-day retention, billed annually; $2.55 on-demand) — indexing is what makes logs searchable and pattern-groupable there, and it's billed on top of $0.10/GB ingestion (datadoghq.com/pricing). Sentry's free Developer plan caps at 5,000 errors/month with 1 user; Team is $26/mo for 50,000 errors (sentry.io/pricing).

Those products do considerably more than this page does — ingestion, retention, alerting, dashboards. This replaces one narrow slice of them: the "what are the actual distinct failures in this dump" question, for a log file already sitting on your disk.

How to use it

  1. Paste log lines into the box, or drop a file on it. The prefilled sample is there to be replaced — delete it and use your own.
  2. Hit Collapse. First run downloads the model (~22 MB) and takes a few seconds; later runs on the same browser reuse the cached copy.
  3. Read the groups top-down — they're sorted by how many raw lines each one absorbed. Click a group to see its masked template and up to 5 real examples.
  4. Drag similarity down to merge more aggressively, up to split more finely, and re-run. 0.80 is the default.

What breaks

  • The cap is your machine, not a quota. Embedding is O(lines), clustering is O(templates²). Input is capped at 20,000 lines here; past a few thousand distinct templates the clustering pass gets slow. Highly repetitive logs stay fast at any size because identical templates are deduplicated before embedding.
  • Model download needs network once. If the Hub is unreachable or you're rate-limited (429), the first run fails — the page reports the error rather than showing fake output. After the first success it works offline.
  • WebGPU if available, CPU otherwise. Falls back to WASM automatically, which is slower but works everywhere.
  • The masking is regex, so it's approximate. An unusual ID format it doesn't recognize stays in the text and can split one real group into several. The similarity model catches many of these anyway, but not all.
  • Grouping is semantic, not causal. Two unrelated errors phrased similarly can land together, and the group counts tell you what's loud, not what's important.

Build this yourself

Two prompts. The first sets up an LLM to build this class of tool — a browser-only analyzer for repetitive machine-generated text. The second is a real, runnable tool-calling example using the same library this page uses.

1. Harness prompt

You are building a single-file, offline-capable browser tool that finds the distinct
signals inside a large volume of repetitive, machine-generated text (logs, stack traces,
crash reports, linter output, test failures). No backend, no API keys, no uploads. It must
be one HTML file that runs from file:// or static hosting.

Stack constraints:
- Inference: @huggingface/transformers (Transformers.js) loaded as an ES module from a CDN.
- Model: a small sentence-embedding model (e.g. Xenova/all-MiniLM-L6-v2, 384 dims, ~22MB
  at q8). Try device:'webgpu' and fall back to WASM on failure.
- No frameworks, no build step, no npm.

CONTEXT MANAGEMENT — this is the part that decides whether the tool works:
The input is far too big to hand to a model whole, but it is also extremely redundant, and
that redundancy is the thing to exploit. Do NOT chunk-and-summarize, and do NOT feed raw
text to a generative model. Use mask -> deduplicate -> embed -> cluster:

  1. MASK the variable parts of each line with regex (timestamps, UUIDs, IPs, hex, hashes,
     file paths, line:col, byte/ms quantities, quoted values, bare integers). This turns
     each line into a stable template string. It is the highest-leverage step: it usually
     removes 80-99% of the apparent variety before any model runs.
  2. DEDUPLICATE on the masked template with a Map, keeping the count and the indices of the
     original lines. Only distinct templates go forward. Discard nothing else — keep the
     originals addressable so the user can always see real examples.
  3. EMBED only the distinct templates, batched. This is the only model call, and its cost
     is proportional to template variety, not to input size.
  4. CLUSTER the embeddings with a single greedy pass over a running centroid list
     (cosine >= threshold joins, else start a new cluster; renormalize the centroid on join).
     Keep only centroids and member indices in memory — never a full N-by-N matrix.

Why this shape and not the alternatives: summarization would destroy the exact strings a
developer needs to grep for, and retrieval assumes you already know the query. Here the goal
is coverage of what is present, so aggregation-by-similarity is the right primitive, and
masking makes it cheap.

Requirements:
- Process the user's own pasted or dropped input. A prefilled sample is fine only as an
  editable starting point.
- Stream progress; never block the main thread without feedback.
- Show the masked template alongside real examples so the user can audit the grouping.
- Expose the similarity threshold as a control — the right value is data-dependent.
- Fail loudly and honestly if the model can't load. Never render placeholder results.
- Export structured JSON so the output can feed another tool.

2. Tool-calling prompt

Transformers.js does support structured tool-calling: apply_chat_template takes a tools array of JSON-schema function definitions and renders them through the model's own chat template (verified in @huggingface/transformers@4.2.0). The catch worth knowing: the template handles tools, so this only works with a model whose chat template was written for tool use — here, Qwen2.5-Coder-1.5B-Instruct. The model emits a tool call as text that you parse and execute yourself; there is no server-side executor.

Write a single HTML file that runs a tool-calling loop fully in the browser with
Transformers.js. Use exactly this API shape — it is the current one for
@huggingface/transformers v4:

<script type="module">
import { AutoTokenizer, AutoModelForCausalLM }
  from "https://cdn.jsdelivr.net/npm/@huggingface/transformers@4.2.0";

const id = "onnx-community/Qwen2.5-Coder-1.5B-Instruct";
const tokenizer = await AutoTokenizer.from_pretrained(id);
const model = await AutoModelForCausalLM.from_pretrained(id, {
  dtype: "q4f16", device: "webgpu",
});

// Tool definitions are plain JSON Schema objects.
const tools = [{
  type: "function",
  function: {
    name: "count_log_pattern",
    description: "Count how many lines in the loaded log match a regex pattern.",
    parameters: {
      type: "object",
      properties: {
        pattern: { type: "string", description: "JavaScript regex source" },
        flags:   { type: "string", description: "Regex flags, e.g. 'i'" },
      },
      required: ["pattern"],
    },
  },
}];

// Your real local implementations, keyed by tool name.
const impls = {
  count_log_pattern: ({ pattern, flags = "" }) =>
    LOG_LINES.filter(l => new RegExp(pattern, flags).test(l)).length,
};

const messages = [
  { role: "system", content: "You answer questions about a log file by calling tools." },
  { role: "user",   content: "How many lines mention a database timeout?" },
];

async function step() {
  // tools + add_generation_prompt are passed to apply_chat_template directly.
  const inputs = tokenizer.apply_chat_template(messages, {
    tools,
    add_generation_prompt: true,
    return_dict: true,
  });
  const out = await model.generate({ ...inputs, max_new_tokens: 256, do_sample: false });
  const text = tokenizer.decode(
    out.slice(null, [inputs.input_ids.dims.at(-1), null])[0],
    { skip_special_tokens: true },
  );

  // Qwen2.5 emits tool calls wrapped in <tool_call>...</tool_call> as JSON.
  const m = text.match(/<tool_call>([\s\S]*?)<\/tool_call>/);
  if (!m) return text;                       // plain answer, done

  const call = JSON.parse(m[1].trim());      // { name, arguments }
  messages.push({ role: "assistant", tool_calls: [{ type: "function", function: call }] });
  const result = impls[call.name](call.arguments);
  messages.push({ role: "tool", name: call.name, content: String(result) });
  return step();                             // let the model use the result
}
console.log(await step());
</script>

Requirements:
- Parse the tool call defensively: models emit malformed JSON sometimes. On a parse failure,
  push a tool message describing the error and let the model retry, with a retry cap.
- Cap the loop (e.g. 5 rounds) so a model that keeps calling tools cannot spin forever.
- Verify the model repo actually ships a tool-use chat template before swapping models —
  if the template ignores `tools`, the definitions silently never reach the model, and it
  will hallucinate answers instead of calling anything.
