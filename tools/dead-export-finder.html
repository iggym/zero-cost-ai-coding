Dead Export Finder

Drop your repo folder onto this page and get every unused export and unreachable file in it — a full import graph built in your browser, typically under a second for a few thousand files. Nothing uploads anywhere; the free tier is your own CPU, and GitHub Pages serves it under a soft 100 GB/month bandwidth cap.

FREE-TIER LIMIT — Analysis is 100% client-side: no API, no key, no quota, no request cap. The only ceiling is browser memory (comfortable to ~20k files) and the GitHub Pages soft limit of 100 GB bandwidth/month + 1 GB site size that hosts this page.

What it replaces

Nothing paid, and that's the point — this is the job Knip and ts-prune do, and both are free and better than this at the deep end (monorepos, plugin configs, auto-fix). What they both cost you is a checkout, an npm install, and a config file before you see a single result. This is for the moment before that: a repo you're deciding whether to revive, someone else's codebase in a review, or a "how bad is it actually" check you want answered in fifteen seconds without installing anything. If the answer is "bad," install Knip.

How to read it


    
  
  1. Unused exports — exported, never imported anywhere, and never referenced inside their own file either. These are the deletion candidates: drop the export keyword and the whole thing usually falls out.
    2. 
  
  2. Used only in own file — the name is used locally but nothing imports it. Not dead code; just remove the export and it becomes a private helper. Kept separate because deleting these would break the build.
    3. 
  
  3. Unreachable files — nothing reachable from your entry points imports them. Check these before deleting: a file loaded by a build tool, a glob, or a string path will show up here as a false positive.
    4. 



Verify anything before you delete it — the fastest check is to remove the export keyword, run your typechecker/build, and see if anything screams.



What breaks


    
  
  • There's no cap to hit, so nothing degrades on quota. Very large repos (20k+ files) will make the tab chug while it reads and parses; it's one pass, so it finishes, it just takes a few seconds.
    • 
  
  • It's a regex-and-heuristics parser, not a TypeScript compiler. It strips comments and string bodies first (so a commented-out export doesn't count), resolves relative paths, index files, TS's .js→.ts rewriting, and @/ + ~/ aliases. It does not read your tsconfig.json paths — custom aliases resolve to nothing, and their targets will look unreachable.
    • 
  
  • Dynamic and namespace imports widen the net, deliberately. If a module is hit by import * as x, require(), or import(), every export in it is marked used, because the tool can't see which names get touched. That means false negatives (real dead code hidden), never false positives, in that direction.
    • 
  
  • Framework magic is invisible. Exports consumed by convention — Next.js getServerSideProps, Vite glob imports, decorators, DI containers, anything referenced by string — look dead and aren't. Default entry globs already cover pages/, app/, configs and tests; add your own for the rest.
    • 
  
  • Public library entry points are excluded from the unused-export list, since their consumers live outside the repo. If you're auditing an app rather than a library, that's a handful of exports it won't flag.
    • 
  
  • export * from re-exports are counted as a wildcard use of the target module — the count of files doing this is shown in the stats, since it's the main reason a number comes back lower than expected.
    • 
  
  • Folder drop needs a Chromium browser or recent Safari/Firefox (webkitdirectory). Firefox handles the "choose folder" button fine but drag-and-drop of a folder is less reliable there.
